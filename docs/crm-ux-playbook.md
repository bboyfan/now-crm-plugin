# NOW CRM 功能設計工作指南：以 Contacts 為基準

這份文件供下一個 CRM 功能開工時使用。它記錄 Contacts 做對的決策、踩過的坑，以及從參考到交付的步驟，不是 FluentCRM 全功能對照表。

**視覺基準是 Contacts 列表與 Contacts 詳情。** 開工前先讀 [專案設計基準](design-system.md)；它把這兩個畫面整理成 `--nowcrm-*` token、版面、元件、狀態與 FluentCRM 對照。新畫面先沿用，不要為單一功能另建一套視覺語言。

- **操作流程看 FluentCRM**：以本機安裝的 FluentCRM Core + Pro 3.3.1 為行為參考。核對入口、控制項順序、預設值、展開時機，以及成功、取消、失敗後回到哪裡。用本機已安裝版本的唯讀原始碼及既有觀察；未觀察到的行為標成「待確認」，不猜。主要對照檔：`plugins/fluent-crm/assets/v3app/src/Modules/Contacts/Contacts.js`（列表）、`plugins/fluent-crm/assets/v3app/src/Modules/Profile/Parts/ProfileOverview.js`（詳情表單）、`plugins/fluent-crm/assets/admin/css/app3.css`（`.fcrm_profile_*` 版面）。只讀，不複製程式或樣式。
- **外觀只看 `design-system.md`**：`docs/design-system.md` 是 NOW 唯一的設計基準，內含 6 個 `--nowcrm-*` token、Contacts 列表與詳情配方、元件與 FluentCRM 對照。Inter、白底、1px 細分隔線、4px 控制項圓角、狀態色只用於狀態（例如已訂閱的綠點）。Fluent 的 8px 圓角、Element Plus 與藍色連結不進 NOW；不需要外部 `DESIGN.md`。
- **資料與權限用 NOW 的契約**：流程可參考，但不可複製 Fluent 的程式或資產、嵌入其畫面，或在執行期依賴 Fluent。沿用 NOW 的 repository、capability、nonce、REST、hooks 與資料表。查實際 owner 和路由時看 [後台畫面與動作對照](admin-map.md)。

## 一個切片，從對照到交付

1. **定義任務結果。** 先寫一句使用者動作與看得見的結果，例如「進聯絡人列表即可掃讀實際資料；勾選後才出現批次工具」。列清楚哪些畫面、資料與副作用不改。
2. **以有代表性的資料對照。** 表格至少看有資料、沒有資料、篩選無結果三種狀態；詳情至少涵蓋已分類與未分類。以資料列、表單與實際結果判斷，不以頁首或按鈕出現當成完成。需比較兩套資料時，用本機合成資料或已授權的對照資料，不寫入既有聯絡人。
3. **先定畫面和狀態，再寫程式。** 先選 Contacts 的列表、詳情或抽屜版面，沿用 [設計基準](design-system.md) 的 token 與元件。記錄初始畫面、觸發點、欄位預設、驗證失敗時是否保留草稿、成功顯示什麼、取消時焦點與篩選回到哪裡。像審查表單一樣確認每顆按鈕真正寫入什麼；沒有真實後端能力的操作不放進選單。
4. **走既有 owner，讓每個操作只提交自己的範圍。** 優先沿用 NOW 的表格、抽屜、對話框和後端動作。區域樣式只套在此次畫面；留意頁面大小上限、跨頁選取、計數口徑、舊連結，以及權限與 nonce。樣式重做不能改變既有資料，也不能用隱藏欄位重送不相干的舊狀態。
5. **交付可手動查看的結果。** 給本機連結、2–4 個關鍵操作與預期結果、實際跑過的最小程式檢查。UI 由使用者手動驗收；不啟動自動瀏覽器驗證。收到明確回饋時，以回饋為準，修該路徑即可，不重跑或重做已接受的畫面。未驗證的操作明確標註；不以 PHP 測試通過代替 UI 驗收。

## Contacts 的決策與可重用模式

| 切片 | 採用的決策 | 後續工作可直接沿用的判斷 |
|---|---|---|
| 入口與新增 | WordPress 側欄顯示聯絡人、名單、標籤；分眾只放 CRM 內。新增由右側抽屜進入，預設已訂閱；選擇待確認時，寄確認信的選項預設不勾選。重複 Email 不覆蓋原資料。 | 瀏覽是預設，建立按需開啟；明確區分儲存資料和對外動作。 |
| 有資料的主列表 | 預設 10 筆，先顯示資料，再讓使用者開進階篩選。只有選取後顯示批次工具。勾滿本頁不等於全選所有結果；全選符合篩選者需另一步。 | 先排出實際首屏資料，再放次要控制項；列表、批次與匯出使用同一個驗證後的篩選範圍，不能在條件出錯時回退成全部。 |
| 聯絡人詳情 | 概覽直接編輯；Email、購買、筆記與動態分頁。儲存資料不覆寫狀態或分類，加入／移除分類只改指定關聯。 | 依工作切分內容與寫入，不靠一張大表單更新整筆記錄。保留原有稽核、安全與資料口徑。 |
| 名單與標籤 | 先顯示表格，新增／編輯按需開啟，CSV 放在更多操作，批次刪除隨選取顯示。名單區分已訂閱與總人數，計數連到相符結果。 | 相似資源共用一個畫面 owner，但篩選、操作與權限必須以實際資源型別為界。 |
| 筆記與動態 | 「新增筆記」放在筆記標題旁。右側抽屜縮短次要欄位區，把空間留給內容輸入，儲存與取消保持可見。筆記仍是內部紀錄，不寄信、不建立任務。 | 密度不是把字與按鈕縮小；先移除用不到的留白與說明，把空間分給主要輸入及操作。 |

主列表第一次改版的反例：同一批本機資料、1365 × 768 的比較中，舊 NOW 首屏完整可見的資料列是 0，FluentCRM 是 7，調整後的 NOW 是 9。教訓是**在定稿前檢查主要內容佔用的空間**，而不是把所有功能都攤在列表上。這是當時的對照結果，不是所有視窗都要達到的筆數。

Contacts 的明確例外是 Company：不提供相關 UI 或新的設定選擇，但保留已存在的資料與已配置的自動化。後續若刻意不做某個 Fluent 行為，也應寫明原因與保留的契約，不把差異含糊寫成已達成完整等同。

```text
使用者任務：從 <入口> 做 <動作>，得到 <可觀察結果>。
不動範圍：<已接受的畫面、資料、權限、外部副作用>。
Fluent 參考：<版本／路由／來源>；<已確認順序與預設>；<未確認或刻意不同>。
設計基準：Contacts <列表／詳情／抽屜>；沿用 <token／class／元件>；<只改的狀態>。
NOW 實作：<現有 owner>；<沿用的元件和資料契約>；<本次變更的狀態>。
手動驗收：<本機入口> → <主要動作> → <預期結果>；另測 <取消或失敗>。
程式檢查：<與變更相符的最窄檢查>；沒有跑的項目明列。
```
